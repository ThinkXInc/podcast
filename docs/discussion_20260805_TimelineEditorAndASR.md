## 2. MLX は量子化されているのではないか

> **ちょっと待って、MLXWhisperを使おうとしているのか。MLXWhisperは8bit量子化されているので、WhisperLargeV3よりも性能が低いんじゃないのか。MLXWhisperが競合するのはWhisperLargeV3Turboであって、ターボはただのLargeV3よりも性能が低いはずだから、結局WhisperLargeV3が最も性能が高いんじゃないのか。ラージＶ３の欠点は時間がかかるということだが、今回は時間よりもとにかく最高の精度を重視している。検討し直してくれ。**

> **Recognition Accuracy (WER) / Whisper Large v3: 7.9% (Industry-leading) / Whisper Turbo: 7.7% (Nearly equivalent) （中略）つまり、Whisper Large V3が最も精度が高いということだろう。**

**オーナーの論点**
- MLX版は量子化されており large-v3 より劣るのではないか
- 競合するのは turbo であり、turbo は large-v3 に劣る
- 時間ではなく精度を最優先する

実物を測りました。`mlx-community/whisper-large-v3-mlx` は `weights.npz` が **3.08GB**
（1.54B×2バイト＝**fp16**）、`config.json` が `n_audio_layer=32 / n_text_layer=32`＝**large-v3 の
フル構成**でした。8bit なら約1.5GB、turbo なら `n_text_layer=4`・約1.6GB なので、どちらでもありません。
**量子化されていたのは従来設定の `WHISPER_COMPUTE="int8"` の方**でした。

180秒の実測は、mlx fp16 が39秒、whisperx int8 が2分47秒、whisperx float32 が3分22秒。
int8 と float32 の文字一致率は **0.9818** で、量子化による劣化は約1.8%。fp16 は Whisper 本来の
推論精度なので、精度要件は fp16 で満たせます。whisperx 側の既定も float32 に変更しました。

**Claudeの回答要点**
- 指摘は原則として正しいが、選んだリポジトリは fp16 フル構成で量子化も turbo でもない
- 量子化されていたのは従来設定の方。変更は int8 → fp16 で精度が上がる向き
- int8 の実害は実測1.8%。whisperx の既定も float32 へ

## 3. チャンク分割は精度を下げるのか

> **気になったのだが、今チャンク分割しているのは、元のWhisperが非常に時間がかかるからであり、新しく、新しいWhisperで速くなっているとしたら、チャンク分割する必要があるのか。チャンク分割した方が精度が下がるのであれば、なるべくチャンク分割を少なくするか、なくしたい。音源は1時間を超えることが十分あり、2時間。とかそういう音源も想定しておく必要がある。音声文字起こしはリアルタイム性はいらないので、時間かかってもいい。1時間とか2時間とか、場合によっては3時間とかかかってもいい。**

**オーナーの論点**
- 分割は速度対策だったはず。速くなったなら不要ではないか
- 分割が精度を下げるなら減らしたい
- 1〜3時間かかってよい。リアルタイム性は不要

同じ6分を「一括」と「3分×2チャンク」で処理して比較しました。**チャンク本体（0〜170秒）の
文字一致率は 1.0000＝完全一致**で、分割は精度を1文字も落としていません。差が出るのは境界の
10秒窓だけでした。

ところが**一括処理の方が幻覚ループに陥り**、285〜355秒の70秒間が「そういう意味があったわけですよね。」の
繰り返しだけになって内容が消えました。原因は分割ではなく、`mlx_whisper` の**CLI** が
`--temperature` を単一値 0 で渡し、Whisper 標準の温度フォールバック（繰り返し検出時に温度を
上げて再デコードする仕組み）を無効化していたことでした。Python API は
`temperature=(0.0,0.2,…,1.0)` が既定なので、API 経由に変えたら再現しませんでした。

分割は残す判断にしました。本体が完全一致で無コストな一方、幻覚が起きたときに被害を
チャンク長に閉じ込められるためです。

**Claudeの回答要点**
- 分割は精度を落としていない（本体の一致率 1.0000）
- 一括の方が幻覚ループを起こした。原因は CLI が温度フォールバックを殺していたこと
- `scripts/mlx_transcribe.py` を作って Python API 経由に変更
- 分割は安全側の保険として残す

## 6. GPT の一次編集をどう位置づけるか

## 8. タイムラインは別画面ではない

> **いや、なんか多分違うのが、別の画面とか作らなくていいんだよ。既存の画面の文字起こしの下にバーが出るというか、文字起こしがタイムラインに変わるってことだよ。文字起こしのその場所がね。別のウィンドウはいらないんだよ。**

## 9. VAD をどう使うか

> **これは後のタイムライン編集UIの話だがSilero VADをまだ使っていないとしたら、このモジュールを使って無音区間を検出し、その区間をタイムライン上に黄色いバーで表示することができるだろう。（中略）文字と文字の位置だけでは無音を判断しにくいので、これはVADで明示的に無音を検出して、それをバーで、バーの色で表現するということだ。**

> **どのVADを使うかは、最も精度が高いものを使え。処理時間は重要ではない。リアルタイム性は全く必要がないからだ。方針転換ではない。無音の爪とは別に、純粋に編集のための表示なので、別と考えていい。**

> **とりあえずハギングフェイスで承認をしておいて。／しておいたよ**

**オーナーの論点**
- VAD で無音を検出し、バーの色で表現する
- 最も精度が高いものを使え。処理時間は問わない
- 無音詰めとは別の、編集のための表示なので方針転換ではない

`docs/無音詰め方針.md` 大原則3 が「音響解析を使わない」としている点を先に指摘しました。ただし
禁止されているのは ffmpeg silencedetect の音量しきい値で、禁止理由「ノイズフロアが高いと誤判定する」を
解決するのが学習済み発話検出モデルなので、矛盾しないと整理しました。

精度優先なら Silero ではなく **pyannote/segmentation-3.0**（2023年版）が本命です。gated モデルのため
利用条件への同意をお願いし、承認後にロードを確認しました。105分を処理して発話1472区間・5054秒
（75.8%）、無音1472区間・1611秒（24.2%）を得ました。

検証で分かったのは、**「えっと」×30 や「いやいや」の反復区間は無音ではない**ことです（VADの発話率
71〜98%）。実際に人が喋っているのに Whisper が聞き取れず反復を吐いた箇所で、私が以前「無音への幻覚」と
説明したのは誤りでした。さらに**文字が無いのにVADが発話と言う箇所が356箇所・合計465秒**あり、
これは Whisper が丸ごと落としている区間です。

**Claudeの回答要点**
- 無音詰め方針との矛盾はない（禁止対象は音量しきい値、用途も別）
- pyannote/segmentation-3.0 を採用（D-020）
- 反復区間は無音ではなく「喋っているのに文字起こしが失敗した箇所」。以前の説明を訂正
- バーが緑なのに文字が空いている場所が「耳で確認すべき危険地帯」として可視化される

## 10. 再生できない — 真因は音源のコーデック

> **スペースを押しても再生できないんだけど。あと赤いバーはそのままでいいよ。**

> **あとスプリットもできない。**

> **再生できません**

> **ALACで音源を保存することが多いので、そのファイルは一回変換する工程を挟んだ方がいいよ。**

**オーナーの論点**
- Space で再生できない。スプリットもできない
- 赤いバー（再生ヘッド）はそのままでよい
- ALAC で保存することが多いので変換工程を挟むべき

原因は3つありました。1つめは**キー操作の対象が決まっていなかった**こと。7本のタイムラインが
あるのに対象をクリック時にしか設定しておらず、何もクリックせずに Space や ⌘D を押すとキーが
素通りしていました（⌘D はブラウザのブックマーク追加に取られていた）。画面中央に最も近い
タイムラインを自動で対象にし、左端の青い縦線で示すようにしました。

2つめは**スプリットしても見た目が変わらない**こと。分割した2つの区間はどちらも「残す」なので
バーが黒くならず、何も起きていないように見えていました。分割位置に `][` のマークを描くようにしました。

3つめが真因で、**音源のコーデックが ALAC（Apple Lossless）**でした。Safari では鳴りますが
Chrome / Firefox は非対応です。Range配信もシークも正常だったのでコードの問題ではありませんでした。
`scripts/make_preview_audio.py` を作り、元音源に触れずに AAC 64kbps mono のコピーを生成する
ようにしました（286MB→52MB）。`transcribe.sh` の最後に自動実行されます。

**Claudeの回答要点**
- 対象未決定でキーが素通りしていた（Space・⌘D 共通の原因）
- スプリットは動いていたが見た目に出ていなかった。`][` マークを追加
- 真因は ALAC。AAC の派生音源を作る工程を追加（D-021）

## 到達点

文字起こしの基盤を Whisper large-v3（mlx・fp16・非量子化）単体に一本化し、Notta は話者ラベルの
付与にのみ使う構成に変えた。判断の決め手は、語単位の正誤ではなく「加工の有無」という
オーナーの読みだった。この過程で、mlx_whisper の CLI が Whisper 標準の幻覚対策を無効化していること、
initial_prompt はどの形式でも捏造か反復を招くこと、pyannote VAD で見ると「文字起こしが失敗した箇所」が
465秒あることが実測で分かった。

編集UIは、文字起こしの表示場所そのものを時間比例レイアウトのタイムラインに置き換えた。文字とバーが
同じ座標系に乗るため、文字間の空白がそのまま無音の長さになり、どの文字を切っているかが一意に決まる。
バーは切らない限り1本のままで、内部を青緑（発話）・黄（無音）・黒（カット済み）で塗り分ける。
未決のカット候補は帯と理由つきで出し、ボタンひとつで黒くしてから端をドラッグして追い込める。

校正用PDFは HTML に役割を譲り、候補のランク付けと一次編集も Claude が担うことになった。
GPT-5.5 Pro への課金は不要と判断された。

残っている宿題は、セグメントの区切り直し（現在の区切りは旧 Notta 版の文字起こしを前提にしている）、
全セグメントを繋いだ1本の書き出し、可逆のまま繋いで最後に1回だけエンコードする方式、
そしてブラウザでの実描画の確認である。
