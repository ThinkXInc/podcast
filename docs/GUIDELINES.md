# GUIDELINES.md — オーナーの包括的な作業指示（podcast）

個別ドキュメント（CLAUDE.md / CLAUDE_GENERAL.md / docs/DECISIONS.md）に収まらない、
**オーナーの普遍的な作業指示**をここに蓄積する。新しい依頼のたびにここを参照して従う。

使い分け:

- **仕様・設計の確定 → `docs/DECISIONS.md`**（正ファイル・オーナー指示原文付き。D-011）
- **仕事のやり方への指示 → 本ファイル**
- **実測して初めて分かったこと → `docs/findings.md`**（同じ思い違いを二度しないための測定ログ）
- **編集の判断基準 → `docs/編集規則.md`** / **無音詰め → `docs/無音詰め方針.md`**

Rules
- オーナーの指示は**原文のまま**記録する。
- 各指示には**解釈・文脈・解決（どう運用するか）**を対にして書く。
- 各記録は番号を付ける。恒久ルール化した一般則は CLAUDE.md / CLAUDE_GENERAL.md に反映し、
  ここからポインタを張る。
- 項1〜13 は他プロジェクト（fabula）の GUIDELINES から継承した汎用指示で、原文・文脈も
  そのまま残してある。文脈に出てくる InDesign 等の固有名は継承元の事情であり、
  指示そのものは全プロジェクトに適用する。項14 以降が本プロジェクトで出た指示。

## 2. 仕様決定は DECISIONS.md を正とし、発案者の指示原文を残す

- **原文**: 「私の注文や指示の原文がどこかに書かれているでしょうか。…おそらくディシジョンズを

- **解釈**: 仕様・設計の確定はすべて `docs/DECISIONS.md` に記録し、各決定に発案者の発言原文

- **本プロジェクトでの反映**: D-011「本ファイルに『オーナー指示原文』列を設け、決定の元になった

## 3. 測ってから提案する。「〜と思う」を確定として記録しない

- **原文**: （オーナーが妥当と認めて転送したレビューより）「今回の撤回は正しかったのですが、
  全74アートボードを調べるのはコマンド1回で、それを提案の前にやっていれば撤回自体が
  要らなかったものです。…1ラウンドの差し戻しがあなたのビルド1回と目視1回を消費する構造なので、
  『測ってから提案する』を先に固定したほうが、結果的に全体が速くなります。」
  ＋オーナー「この意見は妥当性があると思われ、反映すべきものは反映してほしい」
- **解釈**: 提案・設計判断の前に、手元のデータで測定できることは必ず先に測る（実測1回は
  差し戻し1往復より常に安い）。またオーナーの「〜と思う」「〜でもいい」段階の発言を
  「確定」として記録・実装しない（項2の DECISIONS 運用と対）。
- **解決**: 提案には可能な限り実測値（件数・秒数・一致率）を添える。

## 4. 設計提案には「影響する決定番号」と「覆す場合はその明示」を必ず添える

- **原文**: 「まず、提案してくるソリューションがこれまでの議論全体を踏まえていないんじゃ
  ないのか。毎回毎回新しく何か判断するときには、過去の私の発見やこれまでの議論を踏まえた
  上で導き出さなければ、また元に戻ってしまっているんじゃないのか。」
- **解釈**: 新しい提案を出す前に `docs/DECISIONS.md` と突き合わせ、①どの決定に基づくか
  ②どの決定と矛盾・改定になるか、を提案文に明示する。無言の方針反転をしない。
  要求同士が衝突している場合は、衝突をまず可視化してから解決案を出す。
- **解決**: 決定を覆す提案は「D-0xx の△△を、◇◇の理由で改定する」と書いてから内容に入る。

## 5. 発案者の指示した方式を、断りなく別方式に変えない

  別方式のほうが良いと考えたときは、勝手に切り替えず、理由と比較を示して判断を仰ぐ。

## 6. 実測値は「単位」を確かめてから換算する

- **原文**: 「②M-本編:本文 のルビが 19.73Q（正 6.96Q）③Q-クイズ:設問 のルビが未設定（7.46Q を

- **文脈**: 単位を取り違えて、正しく設定されていた値を「要修正」と誤報告した。
  項3「測ってから提案する」の裏返しの失敗。

## 7. 状態を報告する前に、最新を読み直す

- **原文**: 「8.6、どっちが正しいの？最新のファイルを見てるの？この要修正は」

- **解釈**: オーナーは並行して作業している。「要修正」を出す前に、その時点の実データを

- **追記（2026-07-29）版が複数あるときは「最後に触ったもの」でなく「版番号が最大のもの」を選ぶ**。

  - **解釈**: 開いている文書・ディスク上のファイルから1つ選ぶ処理は、開いた順・更新時刻では

## 8. 確認が出る操作は、許可済みの入口にまとめる

- **原文**: 「インデザインの最新状態を読み出すためにいちいち許可してくるんだけど、それを許可なしで
  行うために、Settings.jsonにどのように書けばいいですか？」「osascript を直接叩くのはやめて、
  読み取りを全部スクリプトに寄せます」（2026-07-28）
- **解釈**: 確認プロンプトが出る操作を毎回そのまま叩かない。許可済みの入口（スクリプト）に
  手段をまとめ、必要な機能はそのスクリプトに足す。その場限りのコマンドで確認を挟ませない。
- **本プロジェクトでの該当**: `.claude/settings.json` は `curl` / `wget` / `sudo` が deny。
  HTTP の確認は `venv/bin/python3` の `urllib` で行う（2026-08-05 に curl が拒否され、
  urllib へ切り替えた実例あり）。`.claude/settings.json` 自体は書き換えない（CLAUDE.md）。

## 9. 議事録では発案者の発言を一切省略しない

- **原文**: 「（中略）　中略するな」「オーナーのコメント，指示は完全な原文を保存しろ」（2026-07-29）
- **解釈**: 議事録に発案者の発言を引用するとき、**「（中略）」や要約で縮めない**。
  長くても完全な原文をそのまま載せる。省略してよいのは Claude 側の応答だけ。
  箇条書きで並んだ指摘も1件残らず載せる。
- **本プロジェクトでの該当**: `.claude/skills/meeting-minutes` がこの方針で書かれている。

## 10. 揃わないものは、どちらで揃えるかを決めたら蒸し返さない

- **原文**: 「知ってるよ。これは機械的にやっても揃わないから、InDesign版でだけ揃えればいい
  って言ってるだろ」（2026-07-29）
- **解釈**: 食い違う2つの正本について「どちらを直すか」を発案者が決めたら、以後その食い違いを
  報告し直さない。決定は DECISIONS に書き、実測の報告では「決定済み」として扱う。

## 11. 症状を隠さず、正データの側を直す

- **原文**: 「画像処理は一切するな．画像はそのままオリジナルのまま使うこと．元画像には特別な
  具体的で明示的指示がない限り一切変更してはならない．」（2026-07-30）
- **解釈**: 下流の工程が素材を加工して症状を隠すのは禁止。**症状の出ている場所ではなく、
  正データの側を直す**。「ファイル自体は書き換えていないから加工ではない」という理屈も
  通らない。見え方を変えれば、受け手にとっては加工したのと同じである。
- **本プロジェクトでの該当**: 文字起こしの誤りを表示側で補正して隠さない。ASR の設定か
  元データを直す。カットは `segments.json` の `drops` に記録し、表示だけで消さない。

## 12. 標準機能でできることは標準機能に任せる（上からパッチを被せない）

- **原文**: 「なるべくネイティブの仕組みでできることはそれに任せて上から余計な処理を
  被せないというのが基本方針　パッチを当てるやり方では副作用を増やすから」（2026-07-30）
- **解釈**: 症状に対してスクリプトで後始末をする前に、**使っているライブラリ・ツールに
  その機能が無いかを先に確かめる**。後始末は「標準機能では原理的にできないこと」に限る。
- **本プロジェクトでの該当**: findings.md 1章がまさにこれ。幻覚ループを自前の後処理で
  検出しようとする前に、Whisper が標準で持つ温度フォールバックが効いているかを確かめるべき
  だった（CLI 経由で無効化されていた）。

## 13. オーナーの作業手順を最初に出す（並行作業できるようにする）

- **原文**: 「同時並行で作業できるようマニュアルへ手順追加を先にやってほしいのだが
  　一般規則としてオーナー作業手順をまずやる」（2026-08-03）
- **解釈**: 1つの依頼の中に「オーナーが行う作業の手順」と「Claude 側のスクリプト修正・記録」が
  混ざっているときは、**オーナーの作業手順を最初に仕上げて渡す**。そうすればオーナーが手を
  動かしている間に Claude 側の作業を進められ、全体が速くなる。
- **本プロジェクトでの該当**: `.claude/skills/present-commands` がコマンド提示の作法を定める。

## 14. 記録に、発案者が言っていない理由・解釈を書かない

- **原文**: 「そんなこと言ってないだろ　言っていない勝手な解釈を書くな」（2026-08-04）
- **解釈**: DECISIONS 等への記録で、発案者の発言に**無い理由付けを補って書かない**。
  理由を記録するときは発言の原文をそのまま使う。Claude 側の推測が必要な場合は、原文と
  明確に区別できる形（「解釈」「実測」等のラベル付き）で書き、発案者の判断として書かない。

## 15. 文章データはコードに直書きしない（別ファイルに置いて読み出す）

- **原文**: 「っていうか、なんでPythonに直接文章書いてんの？普通、別のJSONとかに書いといて

  あとで直して」（2026-08-04）
- **解釈**: リストや台帳などの**内容データ（文章）はコードの中に書かず**、JSON や

## 16. 大きな変更の前にブランチを切る

- **原文**: 「今からやる変更は少し大きいので、戻せるようにブランチを分けた方がいいかもしれない。」

- **解釈**: 影響範囲の大きい変更（パイプラインの根幹・ASR の差し替え・UI の新規追加など）に

  切ってから作業する。いつでも戻せる状態を先に作る。
- **文脈**: タイムライン編集UIの新規実装と ASR エンジンの差し替えを同時に始めるにあたっての指示。
- **解決**: `feature/timeline-editor` を作成。着手前に `12e133b` として既存の作業をコミットした。

  （`.claude/settings.json` で deny）。

## 17. 実装の前提が疑わしいときは、実物を測って検証する

- **原文**: 「ちょっと待って、MLXWhisperを使おうとしているのか。MLXWhisperは8bit量子化されて
  いるので、WhisperLargeV3よりも性能が低いんじゃないのか。MLXWhisperが競合するのは
  WhisperLargeV3Turboであって、ターボはただのLargeV3よりも性能が低いはずだから、結局
  WhisperLargeV3が最も性能が高いんじゃないのか。ラージＶ３の欠点は時間がかかるということだが、
  今回は時間よりもとにかく最高の精度を重視している。検討し直してくれ。」（2026-08-05）
- **解釈**: 採用したライブラリ・モデル・設定について仕様の思い込みがあるときは、
  **ドキュメントや記憶ではなく実物を測って確かめる**。モデルなら weights のサイズと config の
  層数、設定なら関数シグネチャの既定値を直接読む。
- **文脈**: 私が `mlx-community/whisper-large-v3-mlx` を「fp16 のフル large-v3」と述べたが、
  その時点では実測していなかった。指摘を受けて実ファイルを確認し、weights.npz が 3.08GB・
  `n_text_layer=32` であることから fp16 フル構成と確定した。同時に、量子化されていたのは
  従来設定の `WHISPER_COMPUTE="int8"` の方だと判明した。
- **解決**: 測定結果は `docs/findings.md` 3章に記録。項3（測ってから提案する）の具体例。

## 18. 精度を優先する。文字起こしに時間はいくらかかってもよい

- **原文**: 「音源は1時間を超えることが十分あり、2時間。とかそういう音源も想定しておく必要が
  ある。音声文字起こしはリアルタイム性はいらないので、時間かかってもいい。1時間とか2時間とか、
  場合によっては3時間とかかかってもいい。」／「チャンク分割した方が精度が下がるのであれば、
  なるべくチャンク分割を少なくするか、なくしたい。」（2026-08-05）
- **解釈**: 文字起こし工程では**処理時間を制約と見なさない**。量子化・蒸留・高速化のために
  精度を落とす選択をしない。ただし「分割をやめる」ことが精度向上になるとは限らないので、
  実測してから決める（項3）。
- **解決**: `config/paths.conf` の `WHISPER_COMPUTE` を `int8` から `float32` に変更し、
  モデルは large-v3 固定（turbo を使わない）と明記した。チャンク分割については実測の結果
  **本体の一致率が 1.0000（完全一致）で精度を落としていない**ことが分かり、むしろ幻覚ループの
  被害範囲を限定する保険として残す判断をした（`docs/findings.md` 2章）。

## 19. 判断材料は、オーナーがその場で判断できる形と量で出す

- **原文**: 「この提示された情報からでは、Nottaが文字起こし原文を加工しているから文字数が単に
  増えているという可能性を否定できない。実際にWhisperが出した文とNottaが出した文を並べて
  5つぐらい比較すれば、私が見てすぐにわかるはずだ。その時に一緒にその時刻も出してもらえれば、
  すぐにわかるだろう。」／「あの、このチャットだけで確認できるように出してくれないかな。」
  ／「もっと長くたくさん出してくれないかな。そんなに短すぎるよ。」／「もっと長い文っていうか、
  まとまったもっと長文を並べて」（2026-08-05）
- **解釈**: 3点ある。第一に、**判断を仰ぐときは実物を並べて出す**。集計値や私の推論ではなく、
  オーナーが自分の目で判定できる生のデータを出す。第二に、**チャット本文に出す**。
  ファイル添付やパス案内で済ませない。第三に、**断片ではなくまとまった長文で出す**。
  20秒程度の窓に切り刻むと文脈が読めない。数分単位の連続した文章として並べる。
- **文脈**: Notta と Whisper のどちらのテキストを採用するかの判断で、私が最初に出したのは
  7〜8秒の断片5件と音声ファイル添付だった。判断材料として短すぎ、かつチャット外だった。
  2分×3ブロックの連続した文章として出し直したところ、「シード」の欠落など決定的な差が
  読み取れるようになった。
- **解決**: 比較・検証の材料は、①チャット本文に、②連続した長文で、③加工や省略なしに出す。
  差分を強調する場合も、原文を削らずに太字などで印を付けるにとどめる。

## 20. オーナー自身が知っていることを、確認材料として出さない

- **原文**: 「私が喋ってるんだから、音源は出さなくてって覚えてるから、テキストだけでいいよ。」
  （2026-08-05）
- **解釈**: オーナーはこのポッドキャストの話者本人である。**発話内容の真偽はご自身の記憶で
  判定できる**ので、音声を切り出して渡す必要はない。テキストを並べれば足りる。
  一般化すると、確認を依頼するときは「オーナーが既に持っている情報」を材料として渡さない。
- **文脈**: 文字起こしの正誤判定のために音源クリップ5件を切り出して送ったが、不要だった。
- **解決**: 文字起こしの正誤確認はテキストのみで行う。音声が要るのは、無音詰めの判断など
  「発話内容ではなく音の状態」を確かめる場合に限る。

## 21. 現状の方式を説明してから、代案と比較する

- **原文**: 「今どのように単語を抽出しようとしているのかわからないが、基本的にはある指示に
  従ってLLMでその長い要約を圧縮するのがいいだろう。つまり、なるべく固有名詞やその話題の文脈を
  よく表すような単語が高い密度で残るようなテキストに圧縮してくれというふうなプロンプトで、
  LLMで処理するのがおそらく精度が高いのではないか。今どのようにしているのか説明し、そして
  私の提案する方法とどちらが良いかを検討してください。」（2026-08-05）
- **解釈**: 代案を検討するときは、**まず現行方式が何をしているかを説明する**。オーナーが
  現状を把握していない状態で比較を出しても判断できない。そのうえで両案を比較し、
  どちらを推すかと**その理由が測定値か推論かを区別して**述べる。
- **文脈**: initial_prompt の作り方について。現行は正規表現による語の抜き出しだったが、
  それを説明しないまま代案の可否だけ述べようとしていた。実測では両案に有意差が出ず
  （どちらも「演役」→「演繹」を正解）、LLM 圧縮を推す理由は測定値ではなく、正規表現方式が
  実際に JSON フィールド名を拾って逆バイアスを作った事実にあることを明示した。
- **注記**: この発言は「〜がいいだろう」「〜ではないか」であり、項3 に従い確定として
  記録・実装していない。実装は比較検討の結果を経て判断する。

## 24. 設定を採用する前に、効かなかったときに何が起きるかを別の区間で確かめる

- **原文**: （項21 の initial_prompt に関する検討の帰結として、実測で判明したこと）
  「イニシャルプロンプトこれはおそらく会話全体の要約などを使うことによって…それはやっても
  いいと思う。」に対し、実測の結果その方針を採らないと判断した。
- **解釈**: ある設定が1区間で効いたことを根拠に採用しない。**効かなかったときの壊れ方**を
  別の区間で確かめる。とくに生成モデルの設定は、平均的な改善より最悪ケースの破壊の方が
  重大なことがある。
- **文脈**: initial_prompt を1区間で試し「『演役』→『演繹』に直った」ことを根拠に採用を
  推奨した。その後ほかの区間で測ると、冒頭120秒が「ご視聴ありがとうございました。」×4 の
  60字だけになって全滅し、プロンプト文そのものを本文として反復出力し、話者が言っていない
  「私は」を挿入して一人称に書き換えていた。オーナーが Whisper を選んだ理由である
  発言忠実性を、まさにその設定が壊していた。
- **解決**: `WHISPER_PROMPT` の既定を無効にした。判断の記録は `docs/findings.md` 5章
  （当初の結論を訂正として明記してある）。項3「測ってから提案する」の続きであり、
  「測る範囲が狭ければ測っていないのと同じ」という追加の戒め。

## 25. 編集データを変更する前に、必ずバックアップを退避する

**原文**（2026-08-08）:

> 何か変更する前に編集データを常にバックアップして退避しろよ

**文脈**: 六本木5-16割り算で、候補分割（index付け替え）に起因する編集消失事故が起き、
復旧作業の過程でも「どの操作の前の状態に戻れるのか」が問われた。復旧前のバックアップは
取ってあったが、ルールとして明文化されていなかった。

**解決**: `data/<ID>/edit/` に触るあらゆる変更（手動修正・スクリプトによる統合・移行）の前に、
`python scripts/backup_edit.py <ID>` で `backup/edit_<日時>/` へ丸ごと退避してから行う。
例外なし。サイト経由の保存は `edit/segments_history.jsonl`（直前状態・最新200件）と
`edit/save_inbox.jsonl`（受信した保存内容の全記録）が自動で保全する。
